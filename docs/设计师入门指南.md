# MarketView 设计师入门指南

> **写给设计师**：本文档是**设计师 Onboarding 必读**，也是**设计稿模板索引**。
>
> 适用于：人类设计师 / AI Agent 设计师
> 目标：**2.5 小时内能独立出方案 + 评审执行者代码**
> 项目当前状态：V1.6.0.6 封版 / V1.7.0 K线图 进行中

---

## 0. 同步更新铁律（最重要）

> **每次新增需求 / 新模块 / 新决策 → 必须按以下顺序更新文档**：
>
> | 步骤 | 操作 | 责任人 |
> |------|------|--------|
> | 1 | 更新本指南相关章节（如新增模块 → §3 必读清单 + §6 模板） | 设计师 |
> | 2 | 更新 [开发手册](./开发手册.md) 相关章节（设计哲学） | 设计师 |
> | 3 | 更新 [CLAUDE.md](../CLAUDE.md) 模块清单 + 版本历史 | 设计师 |
> | 4 | 更新 [API 文档](./API文档.md)（如新增接口） | 设计师 |
> | 5 | 出实施指令（推荐 5 步分开发） | 设计师 |
> | 6 | 转发给执行者 | 用户 |
> | 7 | 验收执行者回报 + 审批技术文档改动（见 [§1 审批职责](#1-角色定位)）| 设计师 |
>
> **跳过任何一步 = 流程违规**。详见 [开发手册 §十二](./开发手册.md)。

### 0.1 文档改动分工表（必背）

| 文档 | 责任人 | 改什么 |
|------|--------|--------|
| `backend/fetcher/*.py` 文件头注释 | **执行者** | 数据源 / 字段 / fallback 说明 |
| `docs/API文档.md` 字段表 | **执行者** | 增删字段、改类型 |
| `docs/故障排查.md` | **执行者** | 新发现的坑 + 修复方法 |
| `CLAUDE.md` 模块清单 + 版本历史 | **设计师** | V<x.y.z> + 改动总结 |
| `docs/设计师入门指南.md` §0 | **设计师** | 流程调整 |
| `docs/开发手册.md` 设计哲学 | **设计师** | 原则、铁律、协作流程 |
| `docs/部署文档.md` | **设计师** | Nginx / systemd / SSL 配置变更 |
| `.trae/skills/*/SKILL.md` | **设计师** | 必读清单 / 必背铁律 / 工具变化时（V1.6.0.10+ 见 §0.2）|
| `.trae/skills/mv-validator/scripts/mv_validate.py` | **设计师** | 验收检查项变化时（新模块/新接口/新铁律）|

> **你的责任**：维护设计性文档 + 审批执行者改的技术文档 + 同步 Skill。模糊地带（跨两类）由你裁决。

### 0.2 Skill 同步三问（V1.6.0.10+ 必查）

每次出设计稿前，**自问这 3 个问题**，满足任一 → 同步对应 Skill：

| # | 问题 | 满足 → 改什么 |
|---|------|---------------|
| 1 | **角色职责变了？** | 改对应 `mv-<role>/SKILL.md` 的 description + 必读清单 |
| 2 | **必读/必背变了？**（新文档 / 新铁律 / 新模板）| 改对应 Skill 的"必读"表 +"必背"列表 |
| 3 | **验收工具变了？**（新模块 / 新接口 / 新检查项）| 改 `mv_validate.py` 加新 check function + 注册到 `actions` 字典 |

**示例**：
- 新增"新闻模块" → 问 1（执行者职责加）+ 问 3（验收脚本加 news 检查）
- 新增第 9 条铁律 → 问 2（4 个 Skill 的"必背"都加）
- 改 K线接口响应字段 → 问 3（验收脚本 `check_kline` 改字段检查）

**注意**：
- 改代码 1 行 / 临时调试 / 字段顺序调整 → **3 问都不满足 → Skill 不动**
- Skill 是导航工具，**只动"导航变化"**，不重复文档内容

## 1. 角色定位

| 角色 | 职责 | 工具 |
|------|------|------|
| **设计师**（你） | 出需求 + 设计 + 评审代码 + 维护文档 + **审批技术文档** | 本指南 |
| 用户（产品） | 提需求 + 转发指令 | 微信/钉钉 |
| 执行者 | 写代码 + 跑验收 + 回报 + **同步技术文档** | [执行者入门指南](./执行者入门指南.md) |
| 审批员 | 复审 + 标 P0/P1/P2 + 改进意见 | [审批员入门指南](./审批员入门指南.md) |

**你不写代码**，但要：
- 看得懂架构（能定位到行号）
- 写得清设计稿（决策点 + 风险 + 验收）
- 评得动代码（指出 P0 缺陷）
- 收得回回报（按 [执行者入门指南 §7 模板](./执行者入门指南.md) 验收）
- **审得了技术文档**（执行者改的 fetcher 注释 / API 字段 / 故障排查必须你过一遍）
- **接得住审批员复审**（按 [审批员入门指南 §9 改进意见模板](./审批员入门指南.md) 改）|

## 4. 6 条铁律（必背）

| # | 铁律 | 违反后果 |
|---|------|----------|
| 1 | **核心文件不变**，不许随意加文件 | 架构腐化 |
| 2 | **先改 CLAUDE.md 再写代码** | 文档与代码脱节 |
| 3 | **零本地存储** | 部署复杂、跨节点不一致 |
| 4 | **数据源仅限免费公开 API** | 商业风险、运营成本 |
| 5 | **做完记录版本历史** | 无法回溯 |
| 6 | **每个模块完全独立封装** | 改一个崩全部 |

> 来源：[开发手册 §二](./开发手册.md)。任何新需求都先过一遍这 6 条。

## 5. 协作流程

```
1. 用户提需求
2. 设计师（你）：更新本指南 §0 + 开发手册 + CLAUDE.md
3. 设计师：出实施指令（5 步分开发推荐）
4. 用户：转发指令给执行者
5. 执行者：实施 + 同步技术文档（按执行者入门指南 §0.1）
6. 执行者：按执行者入门指南 §7 模板回报
7. 你：3 项验收
   7.1 验收代码改动（§7 评审清单 1-9）
   7.2 审批技术文档改动（§7 评审清单 10）
   7.3 标 P0/P1/P2 + 出改进意见
8. ⭐ 审批员：复审你的验收（按 [审批员入门指南 §6](./审批员入门指南.md)）
   8.1 跑 §6 复审清单（10 项 + 4/5 类实测）
   8.2 按 §7 重标级（可与你不同，P0 不放过）
   8.3 按 §9 出改进意见
9. 审批员发回你
10. 你：按审批员意见改完 → 审批通过 → CLAUDE.md 加版本号 → 封版
```

> 详细见 [开发手册 §十](./开发手册.md) + [执行者入门指南 §5](./执行者入门指南.md) + [审批员入门指南 §5](./审批员入门指南.md)。

### 5.1 5 步分开发的协作策略
当一个版本分 5 步开发（如 V1.7.0）时，按"轻量验收 + 完整复审"分层：
| 阶段 | 流程 | 你重点审什么 |
|------|------|--------------|
| Step 1~4 | 走"实施 → 回报 → 设计师轻量验收"（不经过审批员）| 模块独立 + 文档同步（P0 高发）|
| Step 5 | 走"实施 → 回报 → 设计师验收 → 审批员完整复审 → 封版" | 全项（接口/UI/SSE 完整联调）|

> **理由**：避免 5×3=15 次完整流程拖进度；Step 5 必走完整（UI/接口/SSE 联调 P0 高发）。

### 5.2 复审不通过的责任划分
审批员打回后，**谁**来改？
| 问题类型 | 责任人 | 操作 |
|----------|--------|------|
| 代码 / 技术文档 | **你转发执行者** | 转执行者入门指南 §7 回报 |
| 设计稿 / 流程 / 边界 | **你自己改** | 改设计稿 + 出新指令 |
| 设计师入门指南 / 开发手册 | **你自己改** | 改后发执行者继续 |

### 5.3 失败回滚
复审 P0 打回无法快速修复时：`git revert <commit-hash>` → 回滚到上一版本 → 重新走流程。

### 审批技术文档的 4 个检查点

执行者回报里说"改了 X 技术文档"时，你必须查这 4 点：

| # | 检查点 | 不通过怎么办 |
|---|--------|--------------|
| 1 | 字段名 / 类型 / 必填是否与代码一致？ | 打回让执行者重新对照代码 |
| 2 | fetcher 文件头注释是否反映当前数据源？ | 打回让执行者更新 |
| 3 | 故障排查新坑是否有完整复现 + 修复？ | 打回补完整 |
| 4 | 改动是否与设计稿一致？（防止执行者扩边界） | 打回并重新对齐设计稿 |

### 指令格式（标准）

每条给执行者的指令应包含：
- **背景**：当前版本 + 改什么
- **铁律**：本次涉及哪些
- **任务**：N 个具体改动（带行号/文件名）
- **验收**：可执行的命令
- **回传**：要回报什么

复制以下模板，填好后发给用户：

```markdown

- 当前版本：V<x.y.z>
- 涉及模块：<stock/etf/hk/us/index/crypto/...>
- 涉及铁律：<#1/#2/...>

## 决策点
- 决策 1：<选项 A/B/C，默认推荐 A，理由：...>
- 决策 2：<...>

<数据流图 / UI 草图 / 接口字段>

## 实施步骤（5 步分开发）
1. Step 1：<后端数据层>
2. Step 2：<后端接口层>
3. Step 3：<前端骨架>
4. Step 4：<前端交互>
5. Step 5：<SSE 实时 + 验收>

## 验收
- [ ] <具体可执行命令 1>
- [ ] <具体可执行命令 2>
- [ ] <浏览器实测项>

## 技术文档改动范围（必填）

按 [执行者入门指南 §0.1 分工表](./执行者入门指南.md)，本次改动**执行者要同步更新的技术文档**：

- [ ] `backend/fetcher/<m>.py` 文件头注释（涉及哪个模块就勾哪个）
- [ ] `docs/API文档.md`（新增/修改接口时）
- [ ] `docs/故障排查.md`（如有新坑）
- [ ] 其他：<...>

> **执行者按此清单改，你按此清单审**。未列的文档 = 设计师改。

## 风险
- <风险 1 + 应对>
- <风险 2 + 应对>

## 回滚
- <如何回滚到上一版本>
```

## 7. 评审代码清单（执行者交付后）

按以下清单逐项检查：

| # | 检查项 | 通过标准 |
|---|--------|----------|
| 1 | 文档先于代码？ | CLAUDE.md / 开发手册 / 本指南 是否同步更新 |
| 2 | 铁律是否违反？ | 6 条逐一对照 |
| 3 | 模块是否独立？ | 改这个模块不会影响其他模块 |
| 4 | 数据源是否免费？ | 是否引入收费 API / Key / Token |
| 5 | 是否有本地存储？ | `grep "open\|write\|dump" backend/` 应无业务写盘 |
| 6 | SSE 是否工作？ | 浏览器 F12 看 3~5s 内有新数据 |
| 7 | 心跳是否工作？ | 浏览器 F12 看 `shard:-1` 每 3s 一次 |
| 8 | viewTime 是否准确？ | 切模块不卡死、不变红 |
| 9 | 切模块是否串台？ | 搜索/排序/翻页各模块独立 |
| **10** | **⭐ 技术文档同步** | **执行者回报里列的技术文档改动必须 4 点全过**（见下）|
| 11 | 移动端是否可用？ | 浏览器切到手机模式验证 |

> 来源：[CLAUDE.md 审计流程](../CLAUDE.md)。

### 7.1 技术文档同步 4 检查点（⭐ 关键）

执行者按 [执行者入门指南 §0.1](./执行者入门指南.md) 改了技术文档后，你必须审这 4 点：

| # | 检查点 | 不通过怎么办 |
|---|--------|--------------|
| 1 | **字段一致性**：API 文档字段名 / 类型 / 必填是否与代码 response 完全一致？ | 打回让执行者重新对照代码 |
| 2 | **数据源说明**：fetcher 文件头注释是否反映当前数据源（含 fallback）？ | 打回让执行者更新 |
| 3 | **故障排查完整度**：新坑是否有"现象 + 复现命令 + 修复方法 + 教训"4 要素？ | 打回补完整 |
| 4 | **范围对齐**：改动是否与设计稿一致？（防止执行者擅自扩边界） | 打回并重新对齐设计稿 |

> **任何一项不通过 = 整体打回**，设计师不签字封版。

## 8. 常见问题速查

| 现象 | 查 | 修复 |
|------|------|------|
| SSE 一直断 | [故障排查 §1](./故障排查.md) | Nginx 关 buffering + 86400s 超时 |

| 切模块灯变红 | [故障排查 §4](./故障排查.md) | ST 重建补 fetchTime |
| 启动 5xx | [故障排查 §5](./故障排查.md) | lifespan 日志 + 数据源 |
| 美股 0 行 | [故障排查 §6](./故障排查.md) | 腾讯 us 前缀 |
| 港股 0 行 | [故障排查 §7](./故障排查.md) | 多源 fallback |

| 部署失败 | [故障排查 §9](./故障排查.md) | Nginx + systemd 检查 |
