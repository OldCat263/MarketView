## §1 问题

### 1.1 重启后所有缓存丢失

每次服务器重启（systemd restart / crash / 部署）导致：

| 缓存 | 类型 | 丢失后果 | 恢复时间 |
|------|------|---------|---------|
| `_cache`（spot 分片） | 内存 `dict` | 所有模块从 0 开始刷新 | 5-10s |
| `_predict_cache` | 内存 `dict` | predict 全空 | 30-60s |
| `_kline_cache` | 内存 `dict`（TTL 5min） | 所有 K 线重新拉取 | 逐票拉，15-30s |
| `_predict_status` | 内存 `dict` | status 变 not started | — |

### 1.2 K 线重复拉取浪费

历史 K 线一旦收盘即**不可变**（昨日日 K 线永远不变），但每次 TTL 到期后全量重拉，纯属浪费。

### 1.3 Predict 无持久化

重启后 predict 永远为空，直到手动 POST batch 或 daemon 跑完（30-60s 空窗期）。

### 1.4 用户首次打开慢

重启后第一个用户请求所有模块时，数据还没从 API 拉完，看到的是空表/loading。

## §2 方案

### 2.1 总体架构

```
┌────────────────────────────────────────────┐
│            内存缓存（_cache）               │ ← 实时读写
└────────────────┬───────────────────────────┘
                 │ 写入                     │ 加载
                 ▼                          ▼
┌────────────────────────────────────────────┐
│       磁盘缓存（.cache/ 目录）             │ ← 持久化
│  spot_cache.json  │  kline_cache.json     │
│  predict_cache.json │  snapshot           │
└────────────────────────────────────────────┘
```

### 2.2 新增文件

**只新增：** `backend/.cache/` 目录下的 2 个 JSON 文件：
- `.cache/spot_cache.json` — 所有模块 spot 数据 + predict 排行
- `.cache/kline_cache.json` — K 线数据

> ⚠️ **审批员补充确认**：统一使用 `.json` 格式，不引入 `.db`。K 线按 `module_code_period` 去重，count 取最大值缓存。

### 2.3 安全与异常保障

#### 2.3.1 原子写入
所有磁盘写入（`_save_cache()` / `_save_kline_cache()`）必须使用 **tmp + os.rename 原子写入**：
1. 先写临时文件 `.cache/tmp_xxx.json`
2. `os.rename()` 替换目标文件
3. 避免写入中途 crash 导致文件损坏

#### 2.3.2 加载异常降级
`_load_cache()` / `_load_kline_cache()` 必须用 `try/except json.JSONDecodeError` 包裹：
- 磁盘文件损坏、格式不对、或手动修改出错 → 静默降级为空缓存
- 不能阻止启动

#### 2.3.3 并发写安全
`_save_kline_cache()` 使用 `_kline_lock` 保护（复用现有锁），串行化写入。
`_save_cache()` 使用 `_cache_lock` 做 shallow copy 后释放锁，再写磁盘。

#### 2.3.4 `_predict_status` 持久化
`spot_cache.json` 中同时保存 `_predict_status` 字典。加载 predict 缓存时同步恢复 status 为 `{'status': 'done', ...}`，避免显示 `not started`。

#### 2.3.5 磁盘文件兜底
- `.cache/` 目录不存在时自动创建
- `os.makedirs(_CACHE_DIR, exist_ok=True)`
- 确保 `.cache/` 已在 `.gitignore` 中

#### 2.3.6 职责区分
| 文件 | 服务对象 | 用途 |
|------|----------|------|
| `frontend/snapshot.json` | 前端首屏 | 零 HTTP 渲染首页快照 |
| `backend/.cache/spot_cache.json` | 后端重启恢复 | 恢复 `_cache` 到内存 |
| `backend/.cache/kline_cache.json` | 后端重启恢复 | 恢复 K 线缓存 |

#### 2.3.7 Predict Daemon 时序保护（Hotfix：2026-06-28 08:26）

**问题**：daemon 30s 启动后 `_initial_load` 仍在跑（特别是 stock 模块 ~35s），`_cache_lock` 被占，导致 daemon 读到空 spot 缓存 → 跳过 stock → 5 分钟后才重试。

**优化 1：启动延迟从 30s 改为 45s**
- 给 `_initial_load` 中最大模块（stock 5527 只 + akshare 批量）充足完成时间
- 改 `time.sleep(30)` → `time.sleep(45)`

**优化 2：空模块重试机制**
- daemon 每轮跑完全部模块后，检查哪些模块返回空列表
- 对空模块逐个 sleep(30) 后重试（最多重试 2 次）
- 避免冷启动时因时序冲突丢失整轮计算

```python
# 每轮末尾，空模块重试
for m in ('stock', 'etf', 'hk'):
    if not results.get(m):
        for retry in range(2):  # 最多重试 2 次
            time.sleep(30)
            codes = _get_codes_from_cache(m, pool_size=50)
            if codes:
                # 跑 rank_batch + 写缓存 + SSE
                break
```

**预期效果**：
```
T=0s    重启 → 磁盘加载旧数据 ✅
T=45s   daemon 启动 → stock 预加载完成 → stock/etf/hk 全出 ✅
T=75s   万一 stock 仍然空 → 30s 重试 → ✅
之后    每 5 分钟正常循环
```

### 2.4 磁盘格式

**`backend/.cache/spot_cache.json`**（~200-300KB）

```json
{
  "stock": {"shards": [{"data": [...], "ts": ...}], "cols": ["代码","最新价",...]},
  "etf": {"shards": [...], "cols": [...]},
  "hk": {"shards": [...], "cols": [...]},
  "us": {"shards": [...], "cols": [...]},
  "index": {"shards": [...], "cols": [...]},
  "news": {"shards": [...], "cols": [...]},
  "predict": {
    "rank_stock_1d": {"data": [...], "ts": 1782604000}
  },
  "ts": 1782604000
}
```

**`backend/.cache/kline_cache.json`**（~500KB-1MB，按需加载）

```json
{
  "stock_sh600519_1d": {"candles": [["2026-06-12", ...], [...]], "ts": 1782604000},
  "stock_sz000001_1d": {"candles": [...], "ts": ...},
  "stock_bj920080_1d": {"candles": [...], "ts": ...},
  ...
}
```

**cache_key 策略**：`{module}_{code}_{period}`（如 `stock_sh600519_1d`），去重时 count 取最大值。不同 count 请求共享同一缓存（先查过 750 根则 100 根直接复用）。

**条目上限**：最多 500 个 key（LRU 淘汰），防止磁盘膨胀。超过上限时淘汰最久未使用的 key。

### 2.5 Predict Daemon

新增线程 `_predict_daemon`：
- 启动后等待 30s（给 rollers 预热时间）
- **启动前检查**：先检查 `_cached_get('stock')` 是否非空。若空则 sleep 10s 重试，最多等 60s
- 每 5 分钟遍历所有模块调用 `scorer.rank_batch()`
- 每次算完写入 `_predict_cache` + `_save_cache()` + SSE 推送
- 每个模块独立 try/except，失败模块跳过不阻塞
- **首轮完成后立即 `_save_cache()`**，不依赖 30s 定时任务

### 2.6 缓存一致性与过期

| 缓存 | 过期策略 | 说明 |
|------|---------|------|
| spot_cache.json | 每次新写入覆盖 | 每 30s dump，滚动刷新。**必须使用 tmp + os.rename 原子写入**，防止 crash 导致文件损坏 |
| kline_cache.json | 按 code+period 增量追加 | 仅查新蜡烛，append-only |
| predict_cache.json | 每次新写入覆盖 | 5 分钟 daemon 刷新一次 |

重启时：磁盘数据可能**略旧**（最长 30s 的 spot / 5 分钟的 predict），但**绝不空**。rollers 3s 内自动刷新。
