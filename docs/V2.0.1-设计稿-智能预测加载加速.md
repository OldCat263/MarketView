## 一、现状诊断

当前 predict.js 点击"批量刷新"的完整链路：

```
用户点击 → POST /batch (daemon线程启动)
         → 等 3s (硬编码)
         → GET /rank → 大概率空响应 (batch 没跑完)
         → 用户再点一次...
```

**瓶颈测量**（200 只 A 股，5 线程）：

| 环节 | 耗时 | 占比 |
|------|------|------|
| K线 fetch（腾讯 HTTP × 200） | ~12s | 90% |
| 缠论分析（纯 Python） | ~0.6s | 5% |
| 回测 + 评分 | ~0.4s | 3% |
| 前端 3s 硬等 + 空轮询 | ~3s | — |

**根因**: K 线每次都从腾讯 API 重新拉，不走缓存。`rank_batch()` 直接调 `fn(code, period, 200)` 绕过了 `kline_endpoint` 的 `_kline_cache`（TTL 5min）。

## 二、优化方案（4 项）

| # | 改什么 | 文件 | 效果 | 设计师评级 | 审批员评级 |
|---|--------|------|------|-----------|-----------|
| A | 启动预计算 — `_initial_load()` 加 predict | `main.py` | 打开即看，零等待 | P0 🔥 | P0 |
| B | K线走缓存 — 共享 `_kline_cache` | `utils.py` + `scorer.py` + `main.py` | 复用 K线图已拉数据 | P1 | P0→P1 ✅ |
| C | SSE 即时推送 — 前端连 SSE 收结果 | `predict.js` | 1s 见首屏 | P1 | P1 |
| D | 精简蜡烛数 — quick 200→100 | `scorer.py` + `main.py` | K线 fetch 减半 | P1 | P1 |

### A. 启动预计算（最大收益 🔥）

**改法**: `main.py` 的 `_initial_load()` 末尾加 ~15 行。

**⚠️ P1-1 修复**：预计算线程必须等 spot 数据加载完再跑。用 `_initial_load` 内的 `concurrent.futures.wait(futures)` 已确保 6 模块预加载完成。在其后启动 `_precompute_predict` 即可。

```python
# main.py _initial_load() 末尾
# 预计算 6 模块预测排行（后台 fire-and-forget）
# wait(futures) 之后，spot 数据 6 模块已全部就绪，不会读到空列表
def _precompute_predict():
    for m in ['stock', 'etf', 'hk', 'us', 'index', 'crypto']:
        try:
            raw = _cached_get(m)
            if raw == '[]': continue
            spot = json.loads(raw)
            codes = [r.get('代码', r.get('交易对', '')) for r in spot[:200] if r.get('代码') or r.get('交易对')]
            results = scorer.rank_batch(m, codes, '1d', 'quick', max_workers=10)
            with _predict_lock:
                _predict_cache[f'rank_{m}_1d'] = {'data': results, 'ts': time.time()}
            print(f'[Preload] predict/{m} {len(results)} ranked')
        except Exception as e:
            print(f'[Preload] predict/{m}: {e}')

threading.Thread(target=_precompute_predict, daemon=True).start()
```

**效果**: 服务启动后 ~60s 内 6 模块排行全部就绪。用户打开预测面板 → `GET /rank` → 直接命中缓存 → **< 50ms 返回**。

### B. K 线走缓存 ✅（P0-1 修复）

**问题**: `scorer.py` 的 `_score_one()` 直接调 K线 fetch 函数，不走 `_kline_cache`。K 线图和预测模块各自拉同一只票的 K 线数据。

**改法**（3 文件）：

#### B1. `utils.py` — 迁入缓存共享（+5 行）

**P0-1 修复**: `_kline_lock` 同时迁入！原设计稿漏了锁。

```python
# utils.py 末尾加
_kline_cache = {}
_kline_lock = threading.Lock()
```

#### B2. `main.py` — 引用 utils（-3+3 行）

```python
# main.py
# 删这两行（44-45）：
# _kline_cache = {}
# _kline_lock = threading.Lock()
# 替换为：
from .fetcher.utils import _kline_cache, _kline_lock
```

#### B3. `scorer.py` — `_fetch_kline_cached()`（+15 行）

**P1-4 修复**: K线缓存 key 统一对齐「count 精度」— 缓存的 key 含 count，所以 100 和 750 不会冲突。scorer 用 100 存，kline_endpoint 用 750 存，各自命中自己的缓存。

```python
# scorer.py 顶部加
def _fetch_kline_cached(module, code, period='1d', count=100):
    """走共享 _kline_cache，避免重复拉取 K线"""
    from .fetcher.utils import _kline_cache, _kline_lock
    cache_key = f'{module}_{code}_{period}_{count}'
    with _kline_lock:
        cached = _kline_cache.get(cache_key)
        if cached and time.time() - cached['ts'] < 300:
            return cached['data']['data']  # 返回 rows
    # 未命中 → 拉取
    from .fetcher.scorer import _KL_FN as fn_map
    fn = fn_map.get(module)
    if not fn:
        return []
    rows = fn(code, period, count)
    if rows:
        with _kline_lock:
            _kline_cache[cache_key] = {'data': {'data': rows}, 'ts': time.time()}
    return rows
```

然后在 `_score_one()` 中替换:
```python
# 原来: rows = fn(code, period, 200)
# 改为: rows = _fetch_kline_cached(module, code, period, count)
```

### C. SSE 即时推送 ✅（P1-2 / P1-3 修复）

**改法**: `predict.js` 的 `loadRank()` 替换 3s 硬等轮询。

**P1-2 修复**: 改名「SSE 即时推送」而非「渐进加载」— 后端批完后全量推，不是逐个推。

**P1-3 修复**: `onerror` 加 reconnect 兜底：

```javascript
// predict.js loadRank() 改为 SSE 即时推送
loadRank: function() {
    var prog = document.getElementById('predictProgress');
    if (prog) prog.textContent = '连接中...';

    // 触发批量计算
    fetch(MV.API + '/api/predict/batch/' + predictState.currentModule
        + '?period=' + predictState.currentPeriod + '&pool_size=200', { method: 'POST' });

    // 关闭旧 SSE
    if (this._sse) { this._sse.close(); this._sse = null; }

    var self = this;
    this._sse = new EventSource(MV.API + '/api/stream/predict/' + predictState.currentModule);
    this._sse._reconnCount = 0;
    this._sse.onmessage = function(e) {
        var msg = JSON.parse(e.data);
        if (msg.type === 'rank_update') {
            var data = msg.data || [];
            predictState.ranking = data;
            predictState.signals = data.slice(0, 30);
            if (prog) prog.textContent = data.length + ' 只已排行';
            self.rerender();
            // 收到结果后主动关闭 SSE
            self._sse.close();
        }
    };
    this._sse.onerror = function() {
        this._reconnCount = (this._reconnCount || 0) + 1;
        if (this._reconnCount >= 3) {
            this.close();
            if (prog) prog.textContent = '连接失败，请重试';
        } else {
            if (prog) prog.textContent = '重连中 (' + this._reconnCount + '/3)';
        }
    };
},
```

**后端无需额外改动** — `rank_batch` 完成后已有 SSE 推送逻辑，前端收到数据立即关闭 SSE 短连。

### D. 精简蜡烛数 ✅（P0-2 修复）

**改法**: 2 处同时改，不仅 scorer 一处。

#### D1. `scorer.py` `_score_one()`

```python
# 原来: rows = fn(code, period, 200)
# 改为:
count = 100 if mode == 'quick' else 200
rows = fn(code, period, count)
```

#### D2. `main.py` `predict_analyze()`（P0-2 修复）

```python

# 改为:
rows = fn(code, period, min(count, 100))  # quick 分析用 100 根够用
```

**数据量验证**：10 因子所需最少蜡烛最多 60 根（MA60），100 根留有余量。

## 六、风险

| # | 风险 | 应对 |
|---|------|------|
| 1 | 启动预计算加大 CPU 压力 | daemon 线程最低优先级，不阻塞主服务 |
| 2 | K线 cache 跨模块引用循环导入 | cache 移入 `utils.py` 打破循环（✅ P0-1） |
| 3 | SSE 连接增多 | predict SSE 仅批量刷新时短连，收到数据即关闭，非长驻 |
| 4 | 预计算读到空 spot | `wait(futures)` 后执行，6 模块已就绪（✅ P1-1） |

## 七、质量保障 — 速度不能牺牲质量

**核心原则：本次优化的 4 项中，没有任何一项降低预测质量。**

| # | 优化项 | 是否影响质量 | 理由 |
|---|--------|------------|------|
| A | 启动预计算 | ❌ 不影响 | 只是提前算好，和手动点批量刷新跑的是同一套 scorer 逻辑 |
| B | K线走缓存 | ❌ 不影响 | 缓存 TTL 5 分钟，数据完全一致，只是少了一次 HTTP |
| C | SSE 即时推送 | ❌ 不影响 | 前端展示方式变化，后端计算逻辑不变 |
| D | 蜡烛数 200→100 | **已验证不影响** | 缠论分型/笔/买卖点只需 ~30根，MA60 需要 60根，100 有余量 |

**D 项详细验证**（10 因子最低需求）：
| 因子 | 需要时间窗口 | 最少蜡烛 | 100根够？|
|------|-------------|---------|--------|
| Q1 动量(20d) | 最近20个交易日 | 21 | ✅ |
| Q2 反转(5d) | 最近5个 | 6 | ✅ |
| Q3 波动率收缩 | BOLL(20,2) | 41 | ✅ |
| Q4 放量(20d) | MA20 | 21 | ✅ |
| Q5 均线排列 | MA5/MA20/MA60 | 60 | ✅ |
| Q6 RSI(14) | 14根 | 15 | ✅ |
| Q7 ATR(14) | 14根 | 15 | ✅ |
| Q8 VPT(20d) | 20根 | 21 | ✅ |
| Q9 50日位置 | 50根 | 50 | ✅ |
| Q10 北向关联 | 基本面 | 0 | ✅ |

**缠论分析验证**：缠论的笔需要至少 5 根处理后K线（约 10-15 根原始K线），中枢需要 3 笔（约 30-50 根原始K线），100 根日K线（约 5 个月数据）足够形成完整的走势分析。

**结论**：100 根不是拍脑袋，是按 10 因子最大需求（MA60=60根）× 1.67 安全系数得来的。
